# 1. 项目目标

本项目是面向外部 AI 的**小说原文参考服务**：保存保真的小说原文和帮助召回的轻量标记，让 AI 在创作前找到适用原文、阅读必要上下文、形成理解，再完成新作。

用户的正常入口是提供需要分析的 TXT，以及提出后续创作、续写或修订要求。流程分为：

1. **资料准备。** AI 保真整理并导入 TXT；服务同时登记分部准备任务。
2. **连续阅读与认识积累。** 执行中的 AI 逐批阅读目标原文，同时保存具体观察和跨片段作品认识，分别记录证据、连续阅读范围及引用用途；允许某批没有新标记，不要求遍历固定分析维度或输出长篇解读。
3. **可靠保存与分类浏览。** 一批标记、进度与接续信息原子保存；标签和有效标注直接用于浏览。失败回滚本次操作，保留以前成功的批次。
4. **准备核对。** 全部目标阅读处理完成后完成准备。后续补充或修订已有标记时保留已有覆盖；已完成任务可通过准备入口重开并再次完成。
5. **创作查读。** AI 理解新作要求，整体参考先查作品认识或目录，再读适用连续原文，形成新作自身的选择，随后构思与写作；局部问题也可通过分类、标签和标注定位。

AI 自动串联普通步骤，用户不需要逐批安排打标或翻页。自动化覆盖 AI 正在执行任务的期间；AI 停止后不由服务自动唤醒。

原文导入后即可阅读，不等待全书分析或模型索引。阅读处理进度、标注覆盖与文学质量分别判断。

> **原文提供理解依据，标注积累可核对的阅读成果，标签帮助查找；创作通过回读和理解，在新作条件下重新作出选择。**

参考包括内容选择、想象展开与具体语言的联系，以及日常行文、对白组织、叙述距离、节奏和条件性变化，不局限于精彩片段或相似情节。文学效果由用户在实际阅读中判断，不承诺固定提升幅度；新作始终保持自身事实、人物、声音与连续性。

# 2. 系统定位

创作 AI 按题材主动查阅公开背景资料，补充对时代、地域、职业与生活条件的认识，并与文学原文、新作事实相互参照。资料可参与构思、写作及修订，不仅用于成稿后查错；允许阅读发现新的故事可能。该职责由写作 Skill 和宿主已有搜索、阅读工具承担，具体边界见 [Spec 08](../specs/08-分析与创作Skill.md#31-背景资料与生活认识)，不要求扩建背景资料数据库或增加默认 MCP 工具。

本系统不是：

- 普通小说摘要库；
- 以大量 AI 文学评论为主体的数据库；
- 单纯的向量数据库；
- 只保存“作者风格总结”、不保留证据的知识库；
- 将小说压缩成固定写作技巧的模板系统；
- 由后端程序自动进行文学判断的分析引擎；
- 接管新作大纲、世界观、人物档案与全部创作流程的综合平台。

本系统更接近：

> **原文中心的参考库、轻量标记与长篇导航、面向 AI 的分类导航和原文阅读服务。**

长期资产按职责分为：

```text
证据层：SourceFile / 解析正文 / 稳定原文位置
    ↑ 可返回核验
标记层：Annotation 范围 / 标签 / 可核对的观察说明
    ↑ 提供召回线索
发现层：作品认识、分类、标签与标注浏览；关键词检索为独立维护能力

按需资产：Entity / Relation，分别提供身份或证据导航；comparison 标注持续保存作品认识
```

已有说明帮助恢复有依据的理解，并提供继续阅读与核验的线索；文学判断以实际原文为依据。实体与关系继续通过维护入口按需使用，作品认识经默认标注入口发现。

```text
原文负责：核验、纠正、重新理解
简短结论负责：恢复理解、说明写法、减少重复推导
检索与导航负责：找到当前任务值得读取的证据
```

分析任务的接续信息用于恢复工作，不是创作阶段必须整包读取的风格资产。

不采用“大量 AI 分析文章 → AI 摘要 → 原文退居次要位置”的结构。

# 3. 最核心的设计原则

## 3.1 原文始终是系统中心

无论 Annotation、Tag、Entity、Relation还是搜索结果，其中的文学判断最终都应该能够回到真实小说原文。

AI 的分析结论不能取代原文。

使用参考库进行创作时，标签、具体观察与作品认识服务于原文的定位与理解，不计作已完成的原文参考。选中拟借鉴的候选后须实际阅读适用原文及必要上下文；只读说明或搜索摘录就进入依赖该参考的正文创作，违反创作 Skill 的原文阅读要求。压缩后原文不可见时须回读；无法取得必要原文时说明未完成参考，不得用分析摘要代替。具体执行与边界见 [Spec 08](../specs/08-分析与创作Skill.md)。

后续模型升级以后，新的 AI 应该能够重新读取真实原文，而不是被旧 AI 的大段解释锁死。

---

## 3.2 AI 负责文学判断，程序不负责文学判断

以下判断全部交给 Codex / 其他 AI：

- 一次应该读取多少原文；
- 哪里构成一个值得分析的完整范围；
- 哪些原文值得建立 Annotation；
- 应打哪些标签；
- 是否需要创建新标签；
- 哪些人物、地点、物品等值得建立 Entity；
- 哪些远距离文本之间存在 Relation；
- Relation 节点分别承担什么作用；
- 后文是否需要反向补标前文；
- 什么内容值得以后作为创作参考；
- 哪些写法结论值得保存，以及其证据和适用边界；
- 哪些现象属于常态、阶段差异或局部例外；
- 检索证据是否充分，以及何时需要继续读取。

Service 不负责判断：

- 一段是不是一个场景；
- 是否属于伏笔；
- 人物关系有没有升级；
- 某句话是否构成长句写法；
- 某个物件是不是象征；
- 某段是否值得作为文学案例。

---

## 3.3 程序只提供稳定的数据能力

Service 负责：

- 保存原始文件；
- 保存标准化正文；
- 生成稳定的 Section / Paragraph；
- 提供原文读取；
- 保存 Annotation；
- 保存 Tag；
- 保存 Entity；
- 保存 Relation；
- 保存作品认识；
- 保存 Coverage / AnalysisJob 及接续信息；
- 建立原文与标注说明的关键词索引；
- 提供检索；
- 提供 Web 浏览；
- 做技术合法性与正文保真校验；
- 提供可靠写入、重试防重复与进度一致性保障。

---

## 3.4 保存可复用结论，不保存完整推理过程

“分析过程不作为数据库主体”不等于“分析结论尽量不保存”。

有明确复用价值的写法理解，应以简短说明留下，并关联支持它的 SourceRange。说明允许更新或纠正，但不能反过来修改原文。

局部观察不能自动上升为全书规律；待核对推测不能写成已确认事实。程序校验引用和数据结构，AI 负责判断证据是否真的支持说明。

---

## 3.5 读取以充分、适用、互补为目标

创作参考不是“读取越多越好”，也不是“只读摘要就够”。

> **在合理的读取预算内取得足够、适用、互补的原文证据；不足时继续检索，重复结果不反复消耗上下文。**

具体读取量、检索轮数和停止条件由任务及试验决定，不预设适合所有任务的固定配额。

# 4. 小说导入规则

## 4.1 只支持已确认的 Canonical TXT

调用方先创建或选择作品，再按部追加 UTF-8 TXT。每次导入一个完整分部，文件首条非空行为 `分部：名称`，后续使用 `标题：章节名`；其他非空物理行是已确认的自然段。可保留 BOM、CRLF/CR/LF 和正文空白，不归一化字符、裁剪正文或合并硬换行。保真边界从服务收到的完整字节开始，不能证明上传前整理正确。具体限制见 [Spec 02](../specs/02-小说导入与原文读取.md) 与 [Spec 12](../specs/12-作品分部与追加导入.md)。

## 4.2 结构整理由 AI 完成

分部可用独立书名，不强制“第一部、第二部”等编号；没有分部的小说使用一个名为“正文”的默认部。内部卷不建模，也不拼入章节标题；由 AI 在独立准备的导入文件中去掉卷分组标记，保留原章节顺序。卷首序言、引文和正文必须放入章节容器保留，不得随分组标记删除。转换不得覆盖原素材、改写正文或标点、改变自然段和顺序。无章节正文可使用 `标题：正文` 容器。

## 4.3 保存上传原文

每个 Part 保存一份上传字节及解析布局，永久保留、不修改、不覆盖。段落位置指向其章节所属分部的原文件。作品的 source_sha256 为按追加顺序组合的分部文件摘要清单哈希，单文件摘要在 Part；改名不改动原始文件。

## 4.4 校验与事务

预检验证分部格式、作品存在和部名冲突，但不预留名称。正式导入以事务和唯一约束校验并保存分部、文件、目录、段落、统计及回执。相同请求键和同作品同字节返回原快照，不同输入冲突；失败不留下部分分部或成功回执。完整规则见 Spec 12。

# 5. Work 与版本策略

Work 是一个统一分析的故事整体，同一主线的前后几部属于同一 Work。名称全局精确唯一，可按当前版本改名；人物、标注（含作品认识）、关系归作品，可以通过多个 SourceRange 引用不同部。共享世界观本身不意味着自动合并作品，程序不判断或合并身份。

Part 的名称在作品内唯一，名称和顺序独立，顺序仅按导入追加。每次导入一个完整新部，不向已有部补文件、插章节或替换正文。目录写入要求 request_id，改名要求 expected_version；历史回执保持提交时快照。

开发阶段不兼容旧导入协议和旧数据，不迁移原文、分析、回执或索引。使用新的空库部署 0011 后重新导入和分析；迁移遇到业务数据拒绝执行，不自动删除。共享库清理和部署需另有明确授权。

作品屏蔽及整作品物理删除继续按 [Spec 11](../specs/11-作品屏蔽与物理删除.md) 执行，删除范围包含全部分部、原文件、目录写入回执和作品分析，保留全局共享标签及外部文件。

# 6. 原文标准化结构

```text
Work → Part → Section → Paragraph
```

Section 保存所属作品、分部、标题和作品内的稳定追加序号；同名章节合法。Paragraph 保存完整自然段、稳定 UUID、章内序号及上传文件字节位置，不表示场景或文学切片。SourceRange 保持 work_id、section_id 和含两端段落 ID，单个范围不跨章节；多个范围可跨部。

目录及搜索默认覆盖整个作品，可选择 part_id。返回的分部名称与章节名称用于定位，不能替代 UUID。分析任务 whole_work 固定创建时已有段落，part 固定某一部，ranges 固定指定范围；追加不会改变旧目标或继承为已分析。原文和当前分析资产提交后即可阅读与查询，不存在模型索引就绪条件。

# 8. Annotation

## 8.1 Annotation 的定位

Annotation 是：

> **值得回读的原文入口，以及按需保留的、有证据支持且可修订的写法理解。**

Annotation 不是一篇完整文学分析文章，但也不应只有书签而丢失有用的分析成果。

核心组成：

```text
Annotation
├─ kind / title / scope_note：用途、问题与适用范围
├─ references：证据范围、连续阅读范围、每处用途
├─ Tags
├─ Entities（按需关联）
└─ Note：必填的具体观察与联系
```

示例：

```text
原文：
P120-P138

标签：
表达/对白
语境/三人同场
机制/话题恢复
关系/临时合作

实体：
林安
顾成
唐棠

写法说明：
第三人插入实际事务，使原谈话得以恢复。
人物先处理眼前事务，再接回私人问题；动作推迟了回答，
称呼仍保留距离，叙述者也未宣布双方已经释怀。
因此，合作得以推进，但私人隔阂并未在此解决。

适用条件：
需要推动共同事件，但不准备同时解决私人矛盾。

判断边界：
这是该范围中的局部写法；不据此认定人物长期关系已经和好。
```

---

## 8.2 不保存冗长过程，但保存有价值的写法结论

AI 按当前原文和任务需要观察：

- 选择了什么内容，怎样将概括或情境展开成经历、场面与联想；
- 哪些已读经历、关系、世界条件或前后文实际影响本处理解；
- 谁在说话、接哪一句；
- 叙述距离与人物知情范围；
- 关系改变了什么、没有改变什么；
- 动作与对白如何衔接；
- 当前阅读确实需要核对的其他表达问题。

这些完整分析过程、中间草稿和大量重复解释不作为主要长期资产。

只保存有助于后续召回或理解、且能由原文核对的必要说明；不要求为每段解释机制、效果或作者意图。完整分析指南中的维度是按需参考，不是准备任务的逐项清单。

```text
原文范围
+
标签 / 实体 / 关系
+
必要的写法机制、效果、适用条件与判断边界
```

Note 保留值得回读的具体选择、语言组织及有用的上下文联系，说明顺序与长度由观察决定，不设固定栏目。说明原文中的选择怎样成立，不自动将其改写为新作应照做的建议，也不反推作者的真实构思过程。

规则：

- 不以“必须极短”为目标，不设置未经验证的统一字数上限；以便于复用、能核验证据、没有无效重复为准。
- 不只写“细腻、克制、有画面感”等宽泛结论；有价值时应说明具体语言或组织方式。
- 纯身份入口、简单定位或 Relation 节点可以只保留短说明；复杂且有复用价值的案例可以保留数段必要说明。
- 说明应关联实际支持它的 SourceRange；依赖范围以外的已读证据时，补充多处引用并解释联系，或按需关联 Relation。无需附整部背景或完整人物传记，不能凭熟悉作品的记忆补事实。
- 未证实的推测要明确待核对；不要把局部规律写成全书规律。
- 说明可以被后续 AI 修订；不因旧说明存在就跳过必要的原文核验。

## 8.3 Annotation 创建标准

没有固定数量，没有每章最低条数、每万字配额或每维度必须完成的数量。

Codex 的判断标准：

> **如果未来 AI 搜到这条 Annotation，这段原文及其必要说明是否值得用于理解和参考当前写作问题？**

适合建立 Annotation 的情况包括但不限于：

- 典型人物声音；
- 有代表性的对白组织；
- 关系状态或关系变化；
- 叙述方式；
- 长句、抒情或评论；
- 普通但有代表性的转场、动作衔接、日常对白和信息交代；
- 特殊场景处理；
- 重要阶段差异；
- Relation 的关键节点；
- 对后续创作有明确检索价值的完整互动。

不能只选择情绪爆发、漂亮长句和强烈意象。普通段落也是判断作品常态风格的重要证据。

---

## 8.4 Annotation 粒度

原则：

> **一个可以独立理解的最小充分原文范围。**

不能太碎：

```text
P120-P122
P123-P125
P126-P128
```

如果它们本来属于一个完整互动。

也不能贪大：

```text
P120-P400
```

如果其中包含多个完全不同的问题。

---

## 8.5 Annotation 允许重叠

例如：

```text
Annotation A
P100-P140
标签：三人对白 / 话题恢复

Annotation B
P128-P160
标签：关系有限变化
```

这是合法的，同一段原文可以作为多个不同写作问题的检索入口。

合法的重叠标注不等于同一写入请求重试造成的重复记录；后者应由技术机制避免。

---

## 8.6 持续积累作品认识

具体观察与作品认识使用同一 Annotation，kind 分别为 observation、comparison。认识在连续阅读中形成、对照和修订，不等全书结束再写总结，也不以局部技巧数量决定优先级。每条围绕一个有依据的问题，保留内容选择、语言接续、叙述声音与有关条件的联系。

必填 title 命名问题，scope_note 说明实际已读范围与限制，note 保存有用解释。references 的每处 evidence_range 指向证据，reading_range 保留包含证据的连续上下文，role_note 说明此处对判断的作用。多章过程按真实顺序分别引用；同一比较的各处可能是对照或条件依据，不默认都是同一种写法的正例。

通过 library_browse(view=annotations, kind=comparison) 直接发现作品认识，不依赖特殊用途标签。创作参考整体写法时，先查作品认识或目录，再读适用连续原文，形成新作自身的选择，随后构思和写作；局部修订可直接沿标签或坐标阅读。说明帮助接续认识，不替代原文。

范围说明不是阅读进度证明，少量片段不能推出全书频率或作者全部作品的规律。程序不评分文学效果、不自动判定场景完整、不规定阅读配额或写作配方。用户通过实际阅读判断成稿效果，不设置短稿实验前提。

标注契约按 [Spec 18](../specs/18-连续阅读与叙述选择.md) 执行，独立 StyleGuide 已删除。当前升级范围见 [Spec 19](../specs/19-移除语义检索与模型运行依赖.md)：0016 到 0017 只移除废弃检索数据；更早版本经过 0016 时还会清理旧分析。升级前须备份并验证恢复。

---

# 9. AnalysisRecord / Observation 的最终定位

早期讨论过：

```text
AnalysisRecord
Observation
```

本版继续确认：

> **它们不需要作为主要永久数据结构。**

Codex 在分析时仍然可以使用“一个完整分析单元下包含多个观察”的工作方式，但不需要把全部过程性解释逐条永久保存。

最终写入服务时，保留：

```text
Annotation / Tag / Relation / Entity / SourceRange
+
Annotation / Relation 中必要的简短写法结论
+
作品认识
```

任务接续所需的事实入口、待核对线索和操作状态，保存在 AnalysisJob 的恢复信息中，不借此恢复一个大型 AnalysisRecord 报告库。

因此：

> **AnalysisRecord / Observation 属于 AI 的分析工作概念；其有价值的最终结论可以留下，但完整推理过程不是系统必须长期保存的核心资产。**

---

# 10. Tag

Tag 是系统最重要的检索元数据之一。

---

## 10.1 Annotation 与 Relation 都允许 Tag

例如 Annotation：

```text
表达/对白
语境/三人同场
关系/熟悉但有隔阂
```

Relation：

```text
关联/伏笔回收
信息/后文重释
时间/长期跨度
```

---

## 10.2 Tag 是独立对象

概念结构：

```text
Tag
├─ namespace
├─ name
├─ full_name
├─ description
└─ aliases
```

例如：

```text
namespace:
机制

name:
话题恢复

full_name:
机制/话题恢复

aliases:
恢复话题
接回旧话题
重新回到原问题
```

---

## 10.3 标签体系动态增长

Codex 分析时：

```text
准备打标签
    ↓
搜索已有Tag及Alias
    ↓
存在合适标签
    → 直接复用

不存在准确标签
    → 创建新Tag
```

Codex 有权：

> **直接创建正式标签。**

不需要用户审批。

---

## 10.4 防止同义标签爆炸

Codex 创建新标签前必须先搜索现有 Tag。

避免：

```text
机制/话题恢复
机制/恢复旧话题
机制/接回原问题
机制/重新恢复话题
```

实际上描述同一东西。

但是：

> 同义词需要合并，真正不同的近义机制不能为了整齐强行合并。

---

## 10.5 标签定义参与检索

Tag 的名称、description 与 aliases 应可被搜索，用来把自然语言写作问题映射到已有标签。

标签是查找元数据，不替代写法说明或原文证据。标签词表可以增长；浏览分类固定为内容选择与展开、视角与信息、人物与互动、语言与声音、节奏与结构、情绪与氛围，允许多分类，无法归类可暂留未分类。分类不是创作公式，也不要求逐项覆盖。作品专属条件放在标注中，共享标签按整体含义归类；kind=comparison 独立标识作品认识用途。

---

# 11. SourceRange

建议正式建立统一的“原文范围”概念。

例如：

```text
SourceRange
├─ work
├─ section
├─ start_paragraph
└─ end_paragraph
```

用途：

- Annotation 引用；
- Relation Node 引用；
- 搜索结果引用；
- Web 跳转；
- MCP 读取；
- 写法说明和作品认识的证据引用；
- AnalysisJob 接续信息中事实与待核对线索的来源定位。

Annotation 可以拥有多个 SourceRange。

Relation 也可以拥有多个 SourceRange。

---

# 12. Entity

## 12.1 Entity 的定位

Entity 用于解决：

> “这是谁 / 这是什么？”

它不是人物分析档案。

结构保持轻量：

```text
Entity
├─ type
├─ canonical_name
├─ aliases
└─ 必填 Note（按观察需要说明，不设文学字数配额）
```

---

## 12.2 第一版支持的 Entity 类型

```text
character
location
item
organization
concept
```

分别对应：

- 人物；
- 地点；
- 物品；
- 组织；
- 值得长期追踪的特殊概念。

---

## 12.3 Codex 决定哪些对象值得建立 Entity

系统不自动把所有名词建立成 Entity。

例如没必要自动建立：

```text
桌子
杯子
门
鞋子
手机
```

除非这些对象在作品中确实具有长期检索价值。

适合 Entity 的一般情况：

- 重要人物；
- 长期出现人物；
- 关键地点；
- 长期存在的重要物品；
- 重要组织；
- 多章节持续生效的重要概念。

---

## 12.4 不逐字建立所有代词 Mention

不要求：

```text
P123 的“她” = 林安
P125 的“她” = 林安
P127 的“她” = 林安
```

这种细粒度标注。

第一版主要让：

```text
Annotation
Relation
```

关联 Entity 即可。

未来如有明确需求，再增加细粒度 Mention 系统。

---

# 13. Relation

Relation 是系统中处理长篇小说远距离关联的核心对象。

---

## 13.1 Relation 直接连接原文

Relation 不要求必须经过 Annotation。

基本原则：

```text
原文范围
   ↕
Relation
   ↕
原文范围
```

这样即使未来 Annotation 或标签发生变化，远距离原文关系仍然存在。

---

## 13.2 Relation 支持多节点

不能只设计成简单：

```text
A → B
```

因为长篇常见：

```text
第1章
  ↓
第80章
  ↓
第187章
  ↓
第431章
```

或者：

```text
第1章 ─┐
第17章 ├→ 第300章
第89章 ┘
```

因此 Relation 应支持：

```text
Relation
└─ Nodes[]
```

---

## 13.3 Relation Node

每个节点引用一个 SourceRange，并允许一个很短的 Role。

例如伏笔：

```text
Ch1
role = 建立

Ch73
role = 提醒

Ch220
role = 加深

Ch418
role = 回收
```

关系变化：

```text
Ch5
role = 原始状态

Ch68
role = 第一次变化

Ch190
role = 回撤

Ch377
role = 新边界
```

---

## 13.4 Relation 的典型用途

包括但不限于：

- 伏笔与回收；
- 后文重新解释前文；
- 人物关系长期变化；
- 称呼变化；
- 物品长期回返；
- 意象回声；
- 人物声音阶段变化；
- 同一事件的多视角重述；
- 早期判断被后文推翻；
- 重要世界设定的多阶段补充。

---

## 13.5 Relation 保存必要说明，节点按需读取

Relation 保存：

```text
标题
类型
Tags
Entities
Nodes
Note：简短关系说明与必要判断边界
```

说明应帮助 AI 理解“这些节点为何相连、当前确认到什么程度”，避免只保存一个难以解释的关系标题，也不保存冗长分析报告。

读取遵循渐进展开：

```text
取得 Relation 简介、节点清单与 Role
    ↓
按当前问题选择必要节点
    ↓
读取节点原文和必要上下文
    ↓
证据不足时扩大核验范围
```

不要求每次命中都无条件读取整条关系的全部节点。需要判断完整关系演变、核实整体回收或解决节点间矛盾时，应扩大到支持该判断所必需的完整证据链。

未读取的节点不能被当作已在当前任务中核对过的依据。引用已有关系说明时，要区分“库内已有结论”和“本次已经核验的原文”。

关系支持可恢复撤回：撤回后保留说明、节点和关联，普通查询默认排除；显式查询或按 ID 仍可查看，恢复后重新进入普通查询。状态变化和内容修改共用版本检查与可靠写入规则，普通内容修改不隐式恢复已撤回关系。具体接口与契约见 [Spec 05](../specs/05-实体与跨章节关系.md)。

待核对线索可以先进入 AnalysisJob 恢复信息；不能为了方便追踪，就提前写成已经确认的伏笔或 Relation。

---

# 14. 分类标签与原文浏览

默认创作参考走分类 → 标签 → 标注 → 原文，具体契约见 [Spec 17](../specs/17-分类标签与原文浏览.md)。程序提供目录和过滤，外部 AI 判断实际材料是否适用。不能把情境相似等同于写法适用。

## 14.1 分类与标签

分类固定六项，标签可多分类。全部和未分类保证尚未归类的材料仍可发现；分类不能由 AI 新建。标签名称、完整名称、定义和别名支持字面子串搜索；没有标签也可直接浏览标注或部章目录。全库词表包含未使用标签以便复用；指定作品只返回其有效标注使用的标签。计数不是文学重要性排序。

## 14.2 标注过滤

标注默认只查 active，显式可查撤回或全部。多标签 any 默认任一命中，all 才取交集；多分类和多标签不产生重复标注。任一引用符合单作品的分部、章节或 source_range 条件即可命中，不局限首处引用。用户限定作品时不能悄悄放宽。

## 14.3 比较与独立维护能力

作品整体与跨片段比较通过 kind=comparison 查标注，各引用的 role_note 说明其作用；沿 reading_range／read_target 分别阅读，不把证据位置当阅读终点。Entity 和 Relation 仍按需维护，不混入默认分类。

Spec 09 的 source_search、annotation_search 关键词接口保留。reference_query、四路融合、搜索快照及 Spec 10 的语义维护接口已移除；服务不运行模型或后台索引构建。

# 15. 浏览结果原则

library_browse 默认 compact：列表返回作品及部章名、说明摘要和截断提示、标签身份、引用数量、第一处原文坐标。详情返回完整说明、全部引用与可读位置；full 另提供完整维护字段。两种格式不改变成员，详情与原文分开读取。

分页绑定过滤条件；换范围、分类、标签或状态需重新开始。空页只表示此条件没有资产，不证明原文没有参考价值；工具错误不解释为无匹配。标注范围是入口，不是完整场景保证，source_read 按需补上下文并续读完整自然段。

# 16. 浏览范围

分类、标签、标注可省略作品范围以浏览全部可见作品，也可选单 work_id 或非空 work_ids，两者互斥。多作品上限 20。单作品标注进一步支持分部、章节及原文范围，程序核验归属。屏蔽作品不参与结果和计数，显式访问报错。

作品范围不改变标签的全库共享身份。全库标签定义可被多个作品使用，但使用位置和计数只来自当前范围的有效标注。任一／全部标签匹配由调用方明确选择。

# 17. 检索与模型边界

服务不提供 embedding、语义索引构建或语义查询，不部署本地模型。当前原文和分析资产通过分类、标签、标注、目录和关键词被发现；文学理解与材料选择由外部 AI 完成。

0017 清理旧向量、构建回执、旧统一召回表和停用触发器；保留原文、当前标注、标签、关系及分析进度。历史迁移按原语义保留，新空库直接初始化当前结构，避免引入已退役的扩展。具体升级与备份规则见 Spec 19。

---

# 18. 检索的最终目的

Search 不负责直接决定：

> “Codex 应该模仿这一段。”

Search 负责：

> **找到值得 Codex 阅读和核验的候选原文，并提供必要的理解入口。**

最终流程：

```text
理解当前写作问题与新作约束
    ↓
选择允许参考的作品 / 分部 / 章节
    ↓
统一查询并选择候选
    ↓
读取适用原文及必要上下文
    ↓
按需要继续候选、调整查询或回读
    ↓
核验写法及其适用条件
    ↓
结合新作自身事实与叙述契约
    ↓
创作并检查参考效果
```

不要求每次重新读取所有已知证据，也不允许仅凭说明就宣称核对过原文。

停止检索的判断由 AI 负责：核心写作问题已获得足够且互补的参考，必要上下文已补齐，继续返回的主要是重复或不适用内容时，可以开始创作。仍有关键缺口时应继续检索；达到预算后仍不足，应说明覆盖限制，不假装掌握了未读内容。

已有作品认识、具体观察和 Relation 可按具体需要辅助定位，均不构成固定前置步骤。整体气质参考还需要阅读具有代表性的连续原文，不只读取检索排名靠前的片段。

---

# 19. Coverage：长篇处理进度

长篇小说可能几十万或上百万字，因此必须记录处理覆盖状态。

[Spec 07](../specs/07-分析进度与中断接续.md)已确认 Coverage 按分析任务及其固定目标范围隔离，作品分析资产共享。继续分析时恢复原任务；重新开展一轮分析时新建任务，目标范围进度从未处理开始，不自动继承或合并其他任务进度。该能力已实现，要求数据库版本 0005；共享开发库已升级，验证状态见 README。

建议状态：

```text
unprocessed
read
processed
needs_revisit
```

含义：

### unprocessed

尚未处理。

### read

AI 已经读取，但还未完成当前应有标注。

### processed

截至当前已知材料，已经完成这一范围的处理。

### needs_revisit

后续发现需要重新返回检查。

---

## 19.1 processed 不等于冻结

例如：

```text
第2章已经processed
```

读到第400章后发现：

> 第2章某个普通动作其实是长期回声。

Codex仍然可以：

- 回读第2章；
- 增加 Annotation；
- 添加 Tag；
- 创建 Relation。

因此 Coverage 只是进度，不是数据冻结状态。

---

## 19.2 覆盖进度不等于质量证明

Coverage 说明哪里被读取和处理，不直接证明风格判断完整、所有关系已发现，或创作效果已经达标。

某范围经分析后没有适合建立 Annotation 的内容，也可以标记 processed；不能为更新进度而强行制造标注。

范围内本次需要保存的标注、说明、关系和接续信息成功写入后，才能将该范围标记为 processed。写入失败时不得提前推进完成状态。

全书处理完成还应进行针对性的校准与未决事项检查，见第 25 章。

---

# 20. AnalysisJob

AnalysisJob 用于记录一次长篇分析任务的执行状态，以及中断后接续理解所需的最少信息。

默认导入为相应分部登记准备任务，记录完整目标的阅读处理进度和必要接续信息；任务完成不强制完整风格总结或长分析报告。维护入口另保留整作品、分部或指定范围的独立任务能力，目标创建后固定。服务核验进度与保存结果，不判断文学理解是否穷尽。

示例：

```text
作品：小说A
目标范围：全文
当前：Section 127
状态：running

恢复信息：
- 仍影响后续理解的重要事实及 SourceRange
- 尚待核对的线索及 SourceRange
- 已成功保存的位置与下一步操作
```

它不仅回答“读到哪里”，还应帮助新的会话或模型知道“接下来需要沿着哪些已发现的问题继续读”。

---

## 20.1 接续信息的内容

### 已确认的重要事实与原文入口

只记录仍对后续理解有用的事实，并附支持它的原文位置。需要时继续回到原文核对，不把恢复摘要当成最终事实来源。

### 待核对线索与原文入口

记录暂未解释、后文可能需要对照的现象，并明确它尚未确认。

示例：

```text
原文入口：Section 12 / P810-P818
观察：本次称呼与此前不同。
待核对问题：后文是否解释原因，或是否存在持续变化？
当前边界：尚不能认定为伏笔或长期关系变化。
```

线索确认后可补充 Annotation / Relation；被后文否定或判定无继续追踪价值时，应更新其结果，不让旧疑问永久冒充当前未决事项。并非每条线索最后都必须成为 Relation。

### 操作接续状态

记录已经成功保存的范围、尚未完成的操作，以及下一次应从哪里继续。不能只写“接着读”，也不能把仅在上次会话中讨论过、尚未写入的结果当作已落库。

---

## 20.2 接续信息的边界

接续信息是简短的任务恢复记录，不是完整剧情梗概、全文事实库或复杂记忆平台。

AnalysisJob 不保存：

- Chain of Thought；
- 完整的文学推理过程；
- 大量 AI 中间草稿。

第一版可扩展 AnalysisJob 的恢复信息，并引用现有 SourceRange / Annotation / Relation，不要求新增独立记忆服务或强制建立复杂线索实体。

恢复时，AI 应区分已确认事实、待核对推测和操作状态，按需获取相关原文。不得把待核对线索直接写入创作参考中的已确认风格结论。

---

## 20.3 任务完成与恢复

恢复顺序是：检查实际写入结果和 Coverage → 读取接续信息 → 必要时核对原文 → 继续处理。

默认 prepare_finish 检查目标已全部处理，work_ready 检查所有分部任务完成，不以语义索引就绪为门槛。已有作品认识按需核验，不作为完成条件。原作没有解释的问题可以保留为判断限制，不为结束任务编造答案。

小样本验证任务的完成只代表目标样本完成，不代表全书分析完成。

# 21. Web UI

Web 的核心定位：

> **面向用户、以原文阅读为中心，可核验、修订和补充分析成果的工作区。**

用户主要观看、理解 AI 保存的分析成果，修改与调整多交给外部 AI；WebUI 的人工修订与管理为低频可选能力。正式 WebUI 沿用早期目录、原文、标注三栏布局，先完成业务流程与使用优化，再统一打磨视觉；探索展示样稿保留为对照。用户仍可修订标注范围、说明和标签，按意愿创建自己的标签与标注，并删除整部作品。人工参与是可选的，不作为自动准备或召回的审批前提。外部 AI 继续负责导入、分析和创作，网页不接管 AI 执行。

首版页面与交互方案见 [Spec 15](../specs/15-WebUI阅读与标注工作区.md)，已进入正式开发，已提供真实作品库、章节阅读、标签库与独立标注库；已提供原文检索、候选分页及上下文阅读往返，写操作后续实现。下述实体与关系展示保留为能力方向，不因此纳入首版独立页面；具体范围待界面评审。

显示：

- Section 数量；

中间主体永远是小说原文。用户通常顺着小说读，遇到页边标记再查看分析；日常阅读默认关闭分析栏，目录与分析栏可独立收起，保留阅读位置。有标注的段落显示关联数量，正文不整段铺色；点击标记、选择分析不自动跳文，显式点击引用才定位。所选依据用细页边范围线与起止段号说明。

每个节点都可以直接跳回对应原文。先展示关系说明、节点清单和 Role，再按需读取节点正文，不默认一次载入全部远距离原文。

默认打开连续阅读范围，另可定位精确证据；选中标注本身不移动正文，返回时保留原筛选和阅读位置。具体工程验收按 Spec 15、18，不增加文学评分图或报告后台。

# 22. MCP / CLI 职责

外部 AI 负责阅读、文学判断与创作，接口提供稳定的数据操作。默认 MCP 为八项业务工具；细粒度资产 CRUD、手工索引和其他维护能力在显式维护配置中提供，不与日常连接混用。

## 22.1 作品 / 原文

`library_browse` 提供作品、分部、章节、标记和任务导航；`prepare_import` 导入原文并登记准备任务及索引待办；`source_read` 提供完整段落、上下文扩展与分页。作品屏蔽、恢复显示和物理删除仍由 HTTP 管理入口提供，契约见 Spec 11。

## 22.2 Annotation

默认以 `prepare_batch` 新增、修订或撤回标记，同时保存本批阅读进度。修订须使用当前标记版本并完整提交 kind、title、scope_note、note、references 和标签。标记详情通过 `library_browse` 获取；维护入口继续遵循 Spec 04，不把撤回写成单条永久删除。

## 22.3 Tag

准备批次按 namespace/name 精确复用或新建标签，不覆盖共享定义。标签名称、定义和别名参与独立检索线索；单独修订共享标签使用相应维护入口并校验版本。

## 22.4 Entity

实体身份及别名、标记实体关联保留为按需维护能力，契约见 Spec 05。默认准备不强制创建实体，统一查询不提供实体 ID 过滤或自动实体推断。

## 22.5 Relation

跨章节关系保留为按需维护能力，契约见 Spec 05。需要时先取得节点概览，再选择节点回读原文；不把 Relation 自动纳入默认召回，也不要求准备结束前建立关系。

## 22.6 Search

日常入口为 library_browse：categories/tags/annotations 可浏览全库或选定作品；固定分类、标签多选与字面查找帮助发现原文。详情保留每处引用，source_read 负责连续原文；契约见 Spec 17。reference_query 已移除。

默认 `compact` 面向阅读，`full` 返回同一资产或原文的详细字段。数据库或查询失败明确报错，不伪装为无命中。AI 判断材料是否适用于新作，服务不自动作文学选择。

## 22.7 Coverage / Job

`prepare_status` 查询任务、剩余范围与当前索引状态，或按请求键查询提交回执；`prepare_batch` 保存一批成果及进度；`prepare_finish` 核对准备完成；`prepare_cleanup` 仅在明确放弃时清理指定作品。加上第 22.1 节的三个工具和统一查询，构成八项默认职责。

独立任务、Coverage 和 checkpoint 等底层维护能力按 Spec 07 保留，不要求日常 AI 再手工拼装一套准备流程。

## 22.8 不提供文学分析型 MCP 工具

服务使用当前原文与分析资产提供分类浏览及关键词检索，不调用模型完成向量化、文学分析或创作。文学判断由执行中的外部 AI 按任务与 Skill 完成；服务不负责 AI 停止后的自动恢复。

## 22.9 写入重试与进度一致性

- 写入通过请求键及版本校验保证重试幂等、归属和并发一致性；超时查询回执或原键重试，不盲目换键。
- 一次导入、一批标记及进度、一批索引及进度、一次清理分别原子提交；单批失败不留下部分成果，不丢失以前成功的批次。
- 成果和接续信息成功保存后才推进 processed；进度不以标记数量计算，也不等于文学质量证明。
- 合法的重叠标记不因请求去重而被删除。整部作品是准备完成判定和明确放弃时的清理范围，不采用整部暂存发布。

# 23. MCP 与 CLI 共享同一后端能力

服务仅监听本机回环地址，业务 CLI 尚未实现。未来增加入口时仍复用业务规则，不将本文中的能力描述当作可直接执行的 CLI 命令。具体默认接口见 Spec 13、14，基础 MCP 传输见 Spec 03。

# 24. Skill 的职责边界

当前按 [Spec 08](../specs/08-分析与创作Skill.md) 在 `.agents/skills/` 维护 novel-analysis 和 chinese-novel-writing 两份 Skill。各自完整文件夹可独立交付，不依赖开发仓库、其他 Skill 或历史会话。

Skill 补充任务标准与工具约束，依靠 LLM 自身的分析和创作能力。完整分析指南保留在 docs/ 作为维护参考，不整体装入分析 Skill；写作原则只随中文写作 Skill 携带一份，由维护脚本从原文同步。运行 Skill 无需维护源或脚本。

## 24.1 novel-analysis

用户提供待分析 TXT 后，自动保真整理、导入、逐批理解作品具体句行与前后承接，保存写法观察与有证据的跨片段比较，检查已提交进度与必要保存直至准备完成；也支持继续任务和补充修订。目标是帮助创作 AI 理解作品的内容选择与展开、具体语言和叙述声音如何在上下文中成立；剧情人物事实帮助理解，不以整理情节和履历为主要成果。普通步骤无需用户逐批指挥，实体与关系不作为必交成果，独立 StyleGuide 已退役。

保真导入不代表来源内容正确；AI 在准备与分批阅读中主动核对具体来源疑点，区分可见现象和原因推断，不凭猜测改写原文。发现分析错误时实质修订当前说明、引用与标签，整条失效则撤回；保存后回读核验，不以追加免责声明保留错误的有效结论。共享标签定义与标注关联分别维护，普通问题标签不构成原文召回排除规则。

分析包内写法方法与 MCP 流程在首次分析前读取，少量短例仅按实际疑问选读。方法解释内容选择与展开、逐句承接、声音差异、上下文联系和跨片段比较，不要求逐行制表或固定分析维度、篇幅及审美偏好。有依据且有后续价值的比较通过 kind=comparison 标注持久保存，每条围绕一个观察，保留适用范围、条件差异和原文入口，不用整部综合报告代替。

创作参考整体写法时，通过 kind=comparison 及作品范围内 active 标注明确发现这些认识，再读相关连续原文；没有适用条目时从原文建立理解，不把标签存在视为该作品已分析，不把服务错误视为空结果。作品认识与具体观察共用标注契约，不新增服务保留标签或自动迁移旧分析。MCP 参数、版本、分页、幂等与恢复规则在包内维护；仅查看或讨论时保持只读。具体契约和限制见 Spec 08。

## 24.2 chinese-novel-writing

统一承担中文小说构思、创作、续写与定向修订，依照用户目标和新作事实发挥想象力，建立阅读期待，检查实际问题。保留写作原则的事实、人物、因果、声音、参考迁移、表达自由和创作取向。

已连接 NovelLens 时，创作默认主动选择参考并读取适用原文，再确定依赖参考的安排；用户明确不用参考、仅校对文字或当前上下文已有足够原文时按实际需要处理。默认 compact，诊断时使用 full；同问法可续查，改变问法或范围时可提交本次实际已读坐标。参考过程不修改分析资产或推进准备进度。

分类、标签与标注浏览按 Spec 17 实现，具体调用通过写作 Skill 的包内说明提供。背景资料使用宿主已有搜索和阅读能力，区分事实、推断与虚构。必要原文无法取得时如实说明；无需该参考的任务可按实际依据完成。

## 24.3 Skill 与服务严格分工

Skill 指导 AI 怎样工作；MCP / CLI 提供操作入口；Service 保存、读取、搜索和展示数据。文学规则不写死进数据库或后端业务代码。协议验证、实际 AI 流程和文学效果分别记录，某一层通过不代表其他层已完成。

## 24.4 创作项目与参考库的边界

新作品的人物、事实、前文连续性和叙述约束由用户的创作任务提供；本服务负责参考作品的分析与检索，不接管新作的全部管理。

参考作品风格不能覆盖新作明确给定的事实。AI 应判断哪些写法可以迁移、哪些依赖旧作条件，不靠换名字或搬用原剧情完成任务。

# 25. 长篇分析时的增量机制

分析不是：

```text
第1章 → 第2章 → ... → 第500章
然后永远不回头
```

而是允许：

```text
读到第400章
↓
发现与第2章有关
↓
重新读取第2章
↓
确认关联
↓
补Tag / Annotation / Relation
```

因此：

> **长篇知识库是增量完善的。**

后文可以重新解释前文，但建立 Relation 前必须回到真实原文核对。

---

## 25.1 不只允许回读，还要帮助发现何时该回读

后续阅读应结合 AnalysisJob 中仍相关的事实入口和待核对线索，在出现新信息时搜索或返回相关早期范围。分批处理时按本批实际观察查找已有标签及相关标注，区分独立新观察、同一观察补充证据与旧判断修订；不以同人物或同标签强制合并。接续信息完整替换保存，仍有效的未完成操作应带入下一批；接续记录本身不代表标注已更新。默认 MCP 的查找契约见 Spec 16。

```text
前期发现尚未解释的现象
↓
保存待核对问题和 SourceRange
↓
后文出现可能相关的信息
↓
读取前后原文并比较
↓
确认关联 / 修正判断 / 说明仍未确定
↓
更新 Annotation、Relation、导航或接续信息
```

没有预先登记的早期文本，也可以通过原文关键词搜索、目录浏览和连续回读重新发现。不要求前期把所有普通细节都登记成疑似伏笔。

---

## 25.2 全书层面的校准

全书初轮分析结束后，安排有针对性的校准：

- 检查仍待核对的线索，必要时回读对应前后证据；
- 修正早期误判，补充或调整 Annotation / Relation 的说明；
- 存在并使用作品认识时，核对其范围及判断是否与原文相符；不要求为完成准备另建导航；
- 检查 Coverage 与实际成果，明确仍未解决的判断限制。

校准不是机械地第二次逐字重读全书，而是围绕未决问题、阶段差异和代表性证据复核。

不能为了让所有线索“闭环”而强行建立关联；原文不支持的判断应撤回或保持待核对。

# 26. 创作阶段为什么仍然需要 AI 思考

本系统不是让 AI 创作时完全“不思考”。

它省掉的是：

> **每次重新阅读全书、重新寻找案例、重新建立基础风格认识，以及重复推导已经可靠保存的写法结论的成本。**

创作时 AI 仍然需要：

1. 理解当前任务和新作约束；
2. 选择适用原文，按需借助已有标记或导航定位；
3. 按问题检索、选择候选、读取必要证据；
4. 判断哪些叙述机制与语言实现适用于当前作品；
5. 在新作事实和叙述契约中重新组织文本；
6. 检查效果，避免机械替换、照搬原句或导入旧作事实。

因此：

> **系统保存可复用理解并帮助定位证据，AI 负责核验适用性和创造新文本。**

不能走向两个极端：既不应因“以原文为中心”而每次从零分析，也不应因“已有说明”而完全不读相关原文。

# 27. 与《小说作品深度分析与写法标注指南》的关系

该指南用于：

> **指导 Codex / AI 怎样阅读、怎样判断、怎样分析。**

其中：

- D01-D44；
- X01-X12；
- 特殊场景分析；
- 原文证据；
- 上下文补读；
- 关系变化；
- 对话归属；
- 视角权限；
- 普通段落；
- 跨章节关联；

属于按需使用的阅读方法参考，不要求准备任务逐项执行。默认分析 Skill 以保真阅读、准确范围和可核对的写法观察为主；轻量指不制造冗余记录，不省略理解所需的说明与上下文联系。

但是系统数据库不需要把这些全部做成固定字段。

分析指南负责提高：

> Annotation / Tag / Entity / Relation、简短写法说明与作品认识的质量。

而不是让数据库永久保存 AI 的所有推理内容。

本文仅约定系统与指南的职责衔接，不重写 D01-D44、X01-X12 的完整定义或替代指南本身。Skill 从指南中提炼任务标准，不要求运行时携带全部维度和示例。

# 28. 与《中文小说正文写作原则》的关系

[《中文小说正文写作原则》](中文小说正文写作原则.md)主要用于创作阶段。本文约定其与参考库的衔接，不替代该原则全文。

Codex 检索到参考原文以后，可以学习：

- 叙述机制、视角权限、信息释放与组织方式；
- 句长变化、分句组织与叙述节奏；
- 对白组织、动作与叙述的衔接；
- 情绪、意象和评论在具体语境中的语言实现方式。

**不再以“不得继承句法表面”的笼统限制，禁止学习句式组织与语言节奏。** 模仿叙述风格本来就包括对语言实现的理解与应用。

但不能机械搬用参考作品的：

- 人物事实与关系基础；
- 依赖原作设定的道具和意象含义；
- 具体情节及其成立条件；
- 具体原句或逐句换词后的同一表达。

例如，可以学习“先用动作推迟回答，再让对白保持表面正常”的组织方式，但新段落中的动作、动机、人物关系和对白内容必须由新作品本身成立。

核心原则：

> **理解参考原文的内容选择、展开与语言实现，新文本由当前新作品自己的事实、人物、关系、声音和叙述契约重新生成。**

# 33. 项目最终核心原则

## 原文是最终依据

原始文件和稳定正文坐标保留真实证据；任何 AI 说明都可以返回原文核验。

## 可复用理解也是资产

不保存完整推理过程和冗长报告，但保存有原文支持的简短写法结论，减少重复推导。

## 标签是入口

Tag 及其描述、别名帮助 AI 从写作问题进入相关原文。

## Annotation 是精选入口与局部理解

它不仅告诉 AI“这里值得回来读”，也可以说明“此前已经理解出怎样的写法、适用条件是什么”。

## 作品认识持续积累整体理解

既记录日常叙述常态，也区分阶段差异和特殊情境；不把精选高强度片段误当成全书常态。

## Relation 是长篇导航

相隔几十章、几百章的原文可以相连；先看节点概览，再按当前问题读取所需证据。

## Entity 是身份索引

帮助按人物、地点、物品、组织和概念返回原文，不扩张为复杂人物档案。

## Search 不替 AI 作决定

检索支持情境与写法问题，提供候选和匹配来源；文学适用性由 AI 结合原文判断。

## 参考要有证据，读取要有边界

利用已有结论恢复理解，再按需读原文；不足就补读，不为“尽可能多”无条件堆积上下文。

## 长篇处理可以接续与纠正

Coverage 记录进度，AnalysisJob 保留必要接续信息，全书结束后针对性校准，不强行确认未决线索。

## 风格可学习，新作事实不可被替换

允许学习句法组织、语言节奏和叙述方式；不得通过逐句换词、搬用人物事实和情节完成所谓模仿。

## Skill 决定怎样工作

文学方法放在 Skill，不写死进数据库或 Service。

## Service 保持简单可靠

承担存、读、查、连、索引、展示，以及正文保真、合法性校验、可靠写入和进度一致性。

## 以实际创作价值检验能力

逐步实现工程基础、原文和分析资产能力，由用户在实际创作与阅读中判断价值。数据保存成功不能证明检索有效；效果验证应检验检索是否帮助写出更接近目标叙述特征的新文本，并指导后续参数与能力调整。

## 35.1 工程验证与文学判断

工程验收验证当前 Spec 的真实行为：原文保真、引用与阅读范围合法、分页与筛选、版本与幂等、事务回滚、批次进度及迁移边界。必要测试使用独立小型数据，不改写共享原文。

文学效果由用户在真实创作的实际阅读中判断，不以短稿实验、固定模型对照、评分或盲评作为实现和交付的前提。分析样例用于解释方法与边界，不能凭少量示例或工程测试宣称已经学会整部作品的声音。后续发现具体读感问题时，回看所用原文、保存的认识与新作选择，决定是否修订 Skill 或服务。

## 35.2 验收重点

| 验收问题 | 检查内容 |
| --- | --- |
| 找得对不对 | 命中案例是否在写法上适用，而不仅是主题或情节相似 |
| 读得够不够 | 是否补齐理解写法所必需的上下文，是否能按需核对远距离关系 |
| 理解能否复用 | 保存的说明和导航是否帮助恢复认识，是否仍能返回原文纠正误判 |
| 学得对不对 | 新文本是否接近目标叙述距离、对白组织、节奏等特征，同时保持新作事实 |
| 是否把局部当整体 | 是否过度使用情绪高峰写法，能否处理普通日常段落 |
| 检索是否值得 | 与不检索相比，效果是否改善，读取量与调用次数是否可接受 |
| 基础流程是否可靠 | 正文未被改动，中断后能够恢复，重试不会重复标注或错误推进进度 |

这些问题可用于定位用户实际阅读反馈，不要求逐项评分或另做创作实验；工程验收不能替代用户判断。

记录实际使用的参考范围、必要的调用与读取量，以及评阅结果和限制；不要求因此建设独立评测平台。

具体任务数量、质量通过标准与成本预算待试验确定，不预先编造指标或承诺固定改进幅度。
