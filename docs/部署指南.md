# 部署指南

本指南面向首次克隆 NovelLens 的使用者及协助部署的 AI。所有数据库和配置由使用者创建或提供，无需维护者的服务器、密码或镜像归档。常规部署包含 Python 应用与 PostgreSQL / PGroonga / pgvector。全文语义检索另需在本机运行 embedding；普通读取、资产管理与关键词检索无需下载模型。环境检查与参数选择由 AI 按本文执行，项目不提供自动调参器。

当前业务接口要求迁移至 `0014`。配置数据库和 `NOVEL_LENS_EMBEDDING_CONFIG` 后，HTTP / MCP 进程自动维护原文与标记线索索引；embedding 运行时仍按本文独立启动。未配置或模型不可用时，导入和阅读进度可以保存，但不能报告准备完成。服务重启继续消费持久化索引待办，不启动或唤醒外部 AI。准备接口说明见[接口与使用](接口与使用.md#作品准备入口0013)。

默认 MCP 仅提供八项业务工具，AI 经统一召回入口取得参考后阅读原文。维护人员需要原有 CRUD 或手工索引时，可在独立进程设置 `NOVEL_LENS_MCP_PROFILE=maintenance`；普通连接保持默认 business。两个配置的数据库规则相同，配置不是权限隔离。

## 选择运行方式

默认方式：应用在本机 Python 3.12 环境运行，数据库由本机 Docker Compose 创建。HTTP / MCP 监听 `127.0.0.1:8000`，数据库发布 `127.0.0.1:15432`。Dockerfile 从公开 PostgreSQL 基础镜像构建 PGroonga 与 pgvector 扩展，Compose 不引用某台电脑的本地镜像 ID。

如果已经有自己的 PostgreSQL 18、PGroonga 与 pgvector 实例，使用下文“已有数据库”，跳过本机数据库初始化和 Compose。数据库可以共享，NovelLens HTTP / MCP 仍为本机服务。

准备 Git、Python 3.12 和 uv；默认方式另需 Docker 服务和 Compose，支持 Linux 容器。Linux 原生或 Windows WSL 可在同一环境执行命令；Windows 原生应用配合 Docker Desktop 也可按此路径配置。只有 WSL 内可用 Docker 时，优先整套命令在 WSL 执行，不假定 Windows 的 `docker` 命令存在。平台实测范围见文末。

## 首次安装

从项目根目录执行，命令失败时先处理错误，不继续执行后面的迁移和启动：

```text
uv sync --locked
uv run --locked python scripts/init_local.py
docker compose up -d --build --wait
uv run --locked alembic upgrade head
uv run --locked python -m novel_lens
```

Windows PowerShell 先执行 `$env:PYTHONUTF8 = '1'`。不要先复制 `.env.example` 再运行初始化脚本；脚本只接受 `.env` 和 `data/postgres/password` 都不存在的首次安装目录。它生成独立随机密码，写入这两个文件，不打印密码、不连接数据库、不改全局环境。配置已存在时应复用或人工检查，不删除现有配置来强行重跑。

`docker compose up` 创建空数据库，Alembic 建表并启用扩展。应用不自动迁移。当前迁移末端为 `0014`；新数据库需要安装 PGroonga 与 pgvector 0.8.6 的文件以及创建扩展的权限。现有业务库升级前需先备份。

数据库镜像固定 PostgreSQL 18.6 的公开基础镜像摘要、PGroonga 4.0.8 与 pgvector 0.8.6 软件包版本；上游引导包有校验和校验，软件源变化可能导致构建失败，应核对错误而非关闭校验。传递依赖不保证永久不变。依赖来源：[PostgreSQL 官方镜像](https://hub.docker.com/_/postgres)、[PGroonga 安装文档](https://pgroonga.github.io/install/)。

如果 `15432` 被占用，在首次启动前同时调整 `compose.yaml` 的主机端口与 `.env` 中的数据库端口。应用端口可通过 `.env` 的 `NOVEL_LENS_PORT` 修改，MCP 客户端地址也要同步。不要终止不属于当前项目的服务来释放端口。

## 验证与首次导入

1. `docker compose ps` 应显示数据库 healthy。
2. `uv run --locked alembic current` 应显示 `0014 (head)`。
3. 启动应用后，在浏览器访问 `http://127.0.0.1:8000/health` 和 `http://127.0.0.1:8000/works`。前者只验证进程，后者验证数据库读取；新库作品列表为空。
4. 将下面内容保存为 UTF-8 TXT，在 `http://127.0.0.1:8000/docs` 调用 `POST /preparation/import`，JSON 提供新 UUID `request_id`、`name`“部署验证样例”和该 TXT 的绝对 `file_path`。保存返回的 work、part、job ID。可用 `uv run --locked python -c "import uuid; print(uuid.uuid4())"` 生成请求键；超时查回执或沿用原键原输入重试。原文、准备任务和索引待办同时保存，但导入成功不等于 AI 已读完或准备完成。

```text
分部：正文
标题：第一章
月光照在窗沿，她听见门外的脚步声。
她放下杯子，没有立刻回答。
```

这个步骤会在用户数据库保存一部小样例；使用者可选择直接导入自己的已确认 TXT。导入后调用 `GET /works`，读取返回的作品 ID；用 `POST /source/search` 查询该作品中的“月光”，确认原文关键词检索可用。完整参数见接口文档与[接口说明](接口与使用.md)。

在支持 Streamable HTTP 的 AI 客户端中添加 MCP URL `http://127.0.0.1:8000/mcp`，不需要为每个工具分别设置地址。先枚举工具、调用 `library_browse`，再按作品 ID 查询章节或原文。默认服务提供八项业务工具；客户端实际发现的 schema 为调用依据。配置并启动 embedding 后，AI 使用资料准备 Skill 连续阅读和分批保存标记，服务自动索引；通过 prepare_status 和 prepare_finish 核对完成。MCP 成功连接不等于数据库、索引与搜索已经就绪，仍需业务验证。

## 已有数据库

当前版本需要 0014 结构；0011 及以上可升级至 head，0012/0013 增加自动索引与线索同步，0014 增加短期搜索快照及目录世代。不转换 0010 及之前的旧数据或兼容旧导入接口。已有带数据的 0010 及之前实例应另建空库；禁止将升级失败当作清空原库的授权。

不运行 `init_local.py`，也不启动本仓库默认 Compose。将 `.env.example` 复制为项目根目录 `.env`，填入自己管理的数据库连接：

```text
NOVEL_LENS_DATABASE_URL=postgresql+psycopg://USER:URL_ENCODED_PASSWORD@HOST:PORT/DATABASE
```

密码中的保留字符须 URL 编码；TLS 参数按目标数据库实际配置追加，本机默认实例使用 `sslmode=disable`，不能据此要求其他用户关闭远程数据库的 TLS。实例需提供 PGroonga 和 pgvector 0.8.6 扩展文件；普通 PostgreSQL 镜像不自动具备全文检索依赖。仅有连接地址而无访问凭据时，AI 不能自行推导密码。

运行 `uv sync --locked`，确认目标库和备份后执行 `uv run --locked alembic upgrade head`，再启动应用。若共用数据库，只需一个受控升级操作，不由每台电脑并发执行迁移。配置载入优先级为进程环境变量、当前目录 `.env`、默认值，未知 `.env` 字段会拒绝启动。

## 配置与数据位置

| 对象 | 默认位置或行为 |
| --- | --- |
| 应用配置 | 项目根目录 `.env`，UTF-8，Git 忽略 |
| 初始化密码 | `data/postgres/password`，Git 忽略；已有数据库密码不会随文件改变 |
| 数据库数据 | Docker 卷 `novel-lens-local_postgres-data`，挂载容器 `/var/lib/postgresql` |
| 小说原字节、段落、资产、进度 | 数据库中；原文件存于 `part_sources.content` |
| 尚未导入的文件、个人写作草稿 | 用户本机；Git 与数据库均不自动同步 |
| Python 环境 | 项目 `.venv`；换电脑重新安装，Windows / WSL 不共用 |
| 可选 embedding 本机配置 | 根目录 `embedding.local.toml`，Git 忽略；由运行入口读取 |
| 可选 embedding 模型与运行时 | 建议放在 `data/embedding/models/` 与 `data/embedding/runtime/`，Git 忽略 |

默认 Compose 项目名为 `novel-lens-local`。若用 `-p` 或 `COMPOSE_PROJECT_NAME` 自定义项目名，实际卷名也改变；后续命令须使用同一项目名。数据在 Docker daemon 所在机器，Docker Desktop / WSL 的卷不等同于 Windows 工作区下的普通文件夹。

应用配置键：`NOVEL_LENS_HOST`（回环地址）、`NOVEL_LENS_PORT`（默认 8000）、`NOVEL_LENS_LOG_LEVEL`（默认 INFO）、`NOVEL_LENS_DATABASE_URL`、`NOVEL_LENS_MAX_FILE_BYTES`（默认 64 MiB）、`NOVEL_LENS_MAX_REQUEST_BYTES`（默认 65 MiB）。具体默认值也见 `.env.example`。

## 停止、备份与升级

Ctrl+C 停止应用。数据库可执行 `docker compose stop`，随后 `docker compose start --wait`；`docker compose down` 保留卷。`docker compose down -v` 删除数据，不作为重启或升级步骤。

备份默认本机实例时，可先在容器中生成二进制归档再复制，避免跨平台 shell 重定向破坏归档。以下命令适用于默认账号和库名，备份目标文件名每次应不同：

```text
docker compose exec -T postgres pg_dump -U novel_lens -d novel_lens -Fc -f /tmp/novel-lens.dump
docker compose cp postgres:/tmp/novel-lens.dump ./data/postgres/novel-lens-backup.dump
docker compose exec -T postgres rm /tmp/novel-lens.dump
```

备份包含原文及分析资产，应保存到受控位置，不提交 Git。恢复前使用相容的 PostgreSQL / PGroonga / pgvector 环境，先检查归档并在独立空库演练；原库覆盖范围须明确。凭据与未导入本机文件另行保存。

已有部署升级时，先核对版本和目标库并备份，再更新代码、安装锁定依赖、核对镜像变化、执行迁移并复验读取与检索。不要通过删除卷解决升级问题，也不要在未验证时降低数据库版本。

旧版仓库默认 Compose 曾绑定维护者本地镜像 ID、固定容器名和 `novel-lens-postgres-data` 卷。本版改为新实例部署模板，使用不同项目名与默认卷，不会自动接续旧卷。旧部署继续使用原部署目录中已验证的配置；不要直接覆盖后运行新 Compose 并把新空库误认为原数据丢失。迁移旧部署需显式核对原卷、备份与目标配置，不属于新用户首次安装步骤。

## AI 协助部署

可以让 AI：“阅读 README 与部署指南，检查当前环境，部署一个新的本机 NovelLens 实例；已有配置时先核实并复用。”AI 应使用本仓库的同一流程，报告命令失败和未验证事项，无需读取历史会话或维护者的本地环境说明。

需要让后续会话了解本机环境时，可按[本地环境模板](本地环境.example.md)将已核实的工具入口、部署方式、数据位置与验证结果记录到 `docs/本地环境.local.md`；已有记录先核实后更新。此文件不提交 Git，不包含密码，也不参与程序配置加载。普通部署不要求先填写所有字段或运行完整开发测试。

`init_local.py` 只生成数据库密码和应用配置，不检测 CPU / GPU、选择 embedding 参数或修改本机环境记录。可选 embedding 的操作分工与命令见下一节；业务检索的剩余设计见 [Spec 10](../specs/10-原文语义检索与Embedding部署.md)。

## AI 协助准备 embedding

本节用于用户已要求准备独立 embedding 的场景。可以直接把下面的任务说明交给新会话 AI：

> 请阅读本仓库 README、docs/部署指南.md 的 embedding 章节和 embedding.example.toml，为当前电脑准备独立 embedding 服务。先检查是否已有 embedding.local.toml：有则核实并复用，损坏时先说明原因，不覆盖或当作首次安装。没有配置时，使用当前系统命令检查 CPU、可用内存、GPU、驱动及磁盘，有可用且性能合适的 GPU 时优先验证 GPU，否则使用 CPU；参考实测结果选择参数并说明依据。准备固定版本的运行时与模型，写出候选配置，执行真实向量验证；成功后保存本机配置。告知用户所选参数、验证结果、配置和模型位置、启动与停止命令、尚未验证事项。不要改全局环境或自动安装驱动，不擅自更换模型、升级数据库或把本机服务开放到网络。

AI 负责判断与操作，运行入口只负责确定性校验和执行。不能仅凭硬件型号宣称配置可用，也不能把本文的 CPU 示例作为所有电脑的最优配置。

### 1. 检查已有配置和本机资源

已有 `embedding.local.toml` 时先读取并执行下文 `check`，有服务运行时可执行 `status`。普通启动直接复用，不重复下载、测速或调参。首次部署或重新选择后端时，优先使用可用且性能合适的 GPU，没有合适 GPU 时使用 CPU；判断依据为设备、驱动、资源与实际推理，不要求不同后端浮点结果完全一致。损坏配置保留用于诊断，修复或切换另存候选；验证成功后由 AI 说明差异、备份旧文件并替换，`verify --save` 本身从不覆盖。

首次准备时，AI 应检查操作系统与架构、CPU、总内存和当前可用内存、磁盘空间，以及 GPU 和驱动。Windows PowerShell 可按需使用：

```powershell
Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, OSArchitecture, TotalVisibleMemorySize, FreePhysicalMemory
Get-PSDrive -PSProvider FileSystem | Select-Object Name, Used, Free
Get-CimInstance Win32_VideoController | Select-Object Name, DriverVersion
Get-Command nvidia-smi -ErrorAction SilentlyContinue
```

`TotalVisibleMemorySize` / `FreePhysicalMemory` 单位为 KiB。发现 `nvidia-smi` 后再执行 `nvidia-smi --query-gpu=name,driver_version,memory.total,memory.free --format=csv`。不能把 Windows 通用显卡字段当作准确的独立显存或 CUDA 可用性证明。

Linux 可使用 `uname -m`、`lscpu`、`free -h`、`df -h`，有 NVIDIA 工具时再查询 `nvidia-smi`；命令缺失时使用系统等价信息，不为收集信息安装全套工具。参考 [CPU 验证记录](Embedding选型与CPU验证.md)：4096 token 配置实测峰值工作集约 3.5 GiB、提交内存约 4.1 GiB，部署须保留其他应用的资源。CPU 线程数由 AI 结合负载与试运行选择，不直接等于逻辑处理器数；GPU 路径须验证运行时实际列出的设备与可用显存。

### 2. 准备固定产物与候选配置

模型为 Qwen3-Embedding-0.6B Q8_0；固定修订、下载链接、SHA-256 及 Windows CPU 运行时摘要见 [固定实验产物](Embedding选型与CPU验证.md#固定实验产物)。下载或复制已核验文件，建议保存到 `data/embedding/`。下载失败先处理错误，校验失败不得继续。运行时固定 llama.cpp b10964 / commit b29c606e2，解压时保留同包动态库，不只复制可执行文件。

Windows CPU 下载与解压命令见验证记录，下载后将已核验产物放入上述持久目录。其他平台或 CUDA 使用 [b10964 官方发布](https://github.com/ggml-org/llama.cpp/releases/tag/b10964) 中对应系统、架构和后端的构建，核对 `--version` 并记录产物来源及摘要。没有匹配产物、依赖或驱动时明确报告，不自动改用不同版本。

CUDA 候选必须运行所选可执行文件的 `--list-devices`，确认存在 `CUDA0` 等具体设备，再设置 `backend = "cuda"` 和对应 `device`。只有显卡名称或安装了驱动仍不足以通过验证。业务索引支持固定模型与 4096 上下文的 CPU / CUDA；切换时验证分词、维度、归一化、长度边界及实际检索。按 Spec 10 接受合理数值差异：固定对照向量余弦相似度至少 0.999，重复分数差不超过 0.005，并核验明确语义样例的首位命中和原文回读，不要求跨后端排序逐项相同。

AI 参考根目录 [embedding.example.toml](../embedding.example.toml) 写出 `tmp/embedding-candidate.toml`，目录不存在时先创建。路径相对于候选文件目录解析，因此 `tmp/` 下应使用绝对路径或 `../data/embedding/...`，不要原样复制根目录模板的相对路径。

| 字段 | 判断与约束 |
| --- | --- |
| `schema_version` / `model_contract` | 保持模板值，不因换电脑而改变模型契约 |
| `executable` / `model_path` | 指向本机实际文件；支持绝对路径，TOML 中可使用正斜杠 |
| `backend` / `device` | CPU 为 `cpu` / `none`；CUDA 为 `cuda` / 实际设备名 |
| `threads` / `threads_batch` | 正整数，由 AI 选择；CPU 首轮可设相同值，12 不是通用默认值 |
| `context_tokens` | 256—4096；可参考 4096 的资源实测，降低前须考虑输入长度限制 |
| `port` | 空闲本机端口，示例 18081；绑定地址固定为 `127.0.0.1` |

首版并发固定为 1，batch / ubatch token 上限与上下文相同。未知字段会拒绝，不支持任意运行时参数；不对外暴露模型替换、维度或预处理开关。

### 3. 试运行、保存并告知用户

在仓库根目录执行；Windows 先设置 `$env:PYTHONUTF8 = '1'`：

```text
uv run --locked python -m novel_lens.embedding_runtime check --config tmp/embedding-candidate.toml
uv run --locked python -m novel_lens.embedding_runtime verify --config tmp/embedding-candidate.toml --save embedding.local.toml
```

`check` 核对配置、模型哈希、运行时版本及 CUDA 设备，不启动服务。`verify` 临时启动服务，以自编文本生成短、长两条真实向量，检查维度、数值及归一化，再验证超长输入返回 HTTP 400；完成并停止本次子进程后才独占保存配置，文件路径转为绝对路径。stdout 只输出耗时、token 数及维度等元信息。失败或目标已存在时非零退出，不覆盖配置；损坏配置也不会自动初始化。

需要先比较参数时，省略 `--save`，AI 根据试运行与系统资源决定是否调整。需要比较速度时，先用候选配置 `run`，再在另一终端运行 `scripts/benchmark_embedding.py`；命令与缓存控制见验证记录。`--lengths` 要给前缀与特殊 token 留余量，小于配置上下文。AI 使用系统工具观察进程内存与其他应用的响应，测完停止服务，再执行保存命令。不要只因一次较快就称为最优，也不要通过截断原文或更换模型解决资源问题。

验证命令不自动监测整机资源，不是文学效果或完整性能验收。配置保存后，AI 告知用户：后端与参数、选择依据、验证结果、资源观察、配置与模型路径、启动方式及未验证能力。可选地写入 `docs/本地环境.local.md`，该 Markdown 不参与配置加载。

### 4. 日常启动、检查和停止

```text
uv run --locked python -m novel_lens.embedding_runtime run
```

命令读取根目录 `embedding.local.toml`，核对文件与版本并启动服务，真实短文本验证成功后输出 `ready`。终端保持前台运行，Ctrl+C 停止父进程及其创建的服务，正常中断退出码为 130。不管理后台守护进程；启动和验证不下载权重、探测硬件、改写配置或连接数据库。

另一终端执行：

```text
uv run --locked python -m novel_lens.embedding_runtime status
```

`status` 只检查端点健康与模型别名，不启动服务或生成向量，也不证明磁盘产物或跨设备兼容；文件校验使用 `check`。服务未启动、端口错误或标识不符时非零退出。不要终止其他服务来释放端口。

文件损坏、版本不符或 CUDA 不可用时先核对错误与配置，修复后重新验证，不静默回退 CPU 或切换模型。传给子进程的 `LLAMA_ARG_*` 环境覆盖会被清除，以配置与固定参数为准，不修改全局环境。

换电脑后重新检查资源并准备本机配置，优先验证可用且性能合适的 GPU，保留相同模型契约。通过后端兼容性验证后，CPU/GPU 可复用同库已有向量与构建进度；其他设备仍需各自验证，不能仅凭维度相同认定兼容。

## 启用全文语义检索

数据库环境需包含 pgvector 0.8.6，新库迁移至 0014；已有 0011/0012/0013 库升级至 head。0011 引入 Work → Part → Section → Paragraph，不兼容旧接口，不转换旧原文、分析或索引；非空旧库升级会明确拒绝，不会自动删数据。已有用户应另建空库后升级、重新导入分析，保留旧实例供查阅；如要清空旧库，须另行明确授权目标和范围。0011 不提供降级转换。新用户按本指南初始化即可；不将本机配置直接套用到共享库。

按上节准备并验证 `embedding.local.toml`，业务接入要求经验证的 CPU / CUDA 后端、4096 上下文、固定权重与运行时。应用不启动或下载模型，分别在两个终端运行：

```text
uv run --locked python -m novel_lens.embedding_runtime run
uv run --locked python -m novel_lens
```

启动 NovelLens 前，在项目 `.env` 中增加以下可选配置（路径相对于应用工作目录）：

```dotenv
NOVEL_LENS_EMBEDDING_CONFIG=embedding.local.toml
```

通过 `semantic_index_get` 按 kind（fulltext / annotation）查看作品索引；明确需要构建时使用 `semantic_index_create` 和有限批次的 `semantic_index_build`，达到 ready 且动态 coverage.complete 为 true 后调用 `source_semantic_search`。完整参数见[全文语义接口](接口与使用.md#全文原文语义索引与查询)。索引与向量保存在 PostgreSQL，权重保存在本机；复制代码或模型不等于复制业务数据。只需基础功能时省略该配置，无需启动 embedding。
